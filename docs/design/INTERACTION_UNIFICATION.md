## 按交互语义统一

承载方式必须按具体任务选择，不能因为某种弹层“好看”就到处使用。直接开关/简单选择优先原位生效；少量局部选项用就近菜单或展开；短暂处理当前对象用底部面板；多字段或多步骤任务进入独立页面；删除/覆盖/放弃修改用说明后果的确认；成功优先靠界面结果表达，仅在结果不明显时补轻提示。每个入口都须结合位置、内容长度、下一步和退出方式复核，不机械套表。

1. 普通点按：即时中性反馈，不叠加缩放或弹跳。
2. 同级选择：选中指示器跟随目标，快速切回可中断；不为每个卡片添加入场动画。
3. 层级页面：前进/返回空间关系明确，保留预测性返回取消/完成。
4. 原位展开：共用无回弹折叠，入口、展开内容与收起关系清楚。
5. 底部面板：课程详情、选择和上下文操作；统一容器、拖动柄、间距与安全区。
6. 居中弹窗：短确认、删除、放弃修改；同一套标题、正文、主次按钮和危险状态。

## 执行顺序

第一轮样板已开始落地，具体入口、行为变化和仍待覆盖的范围见 [交互样板记录](INTERACTION_PILOT.md)。组件种类暂不扩张；优先复用既有面板、弹窗、按钮，补齐退出确认、处理中禁用和跨容器衔接等共同行为。

### 每个交互必须登记的契约

| 项目 | 要回答的问题 |
| --- | --- |
| 用户意图 | 此按钮或部件解决什么问题，是否重复已有入口？ |
| 触发和反馈 | 点按、长按、拖动、键盘分别做什么；怎样确认已触达？ |
| 结果和承载方式 | 直接完成、原位展开、菜单、底部面板、短确认或新页面；为何采用这种方式？ |
| 页面关系与动效 | 是同级切换、进入详情还是覆盖当前内容？出现和消失是否配对？ |
| 数据时机 | 即时保存还是明确提交？忙碌时是否允许重复操作？失败后如何恢复？ |
| 返回和取消 | 顶部返回、系统返回、手势、点击外部是否一致；哪些修改保留或丢弃？ |
| 状态与设备 | 返回后滚动位置、选中项、草稿如何恢复；旋转和分屏是否改变任务？ |

### 已核对的路由关系（不是全部按钮审计完成）

依据 `SleepyNavHost.kt`：主 tab 同级切换；设置首页 → 课表显示 → 节假日；设置首页 → 通用；小组件列表 → 指定实例编辑；全部课表 → 课表编辑；作息表列表 → 作息编辑；关于 → 开源许可。它们共享 NavDisplay 的进入/返回转场。

需要特别评估的现状：AddCourse 保存后弹栈并切到课表 tab，进入来源不一定是课表；课程编辑会话丢失时会退栈，不能宣称所有编辑状态均可恢复。新课表/作息的放弃流程有单独路由处理，改动返回动画时不能绕过数据处理。后续要把这些实际行为写进各操作契约，再决定是否调整，不能仅替换转场曲线。

先做“课程详情 → 编辑/调整 → 保存或取消”与“设置 → 子页 → 选择/返回”两条高频链路，再推广其他调用方。每次变更共用组件要检查键盘、长英文、1.5 倍字体、窄分屏、TalkBack 与连续操作。不根据源码宣称观感已统一。

玻璃保持独立 Debug 原型，不接生产设置。先完成以上样板体验，再进行真正设备上的材质对照，避免用装饰掩盖基础交互差异。

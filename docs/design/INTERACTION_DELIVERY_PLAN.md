# Classy UI 与交互后续执行总计划

更新：2026-10-12。状态：第二阶段进行中。本文件是后续工作的唯一调度入口；设计规范、源码台账和设备记录分别提供规则与证据，不再各自维护互相竞争的“下一步”。

## 目标与范围

主线：建立并落实简洁、美观、统一、符合直觉的 UI 与交互体系。组件按操作目的选择，动效表达关系，所有页面进入/退出连续流畅；手机、平板、可变窗口保持可用。

完成不是“改了多少文件”或“测试数量增加”，而是每条用户操作链的组件选择、状态规则、视觉连续性、性能与适配均有结论和证据。基础验收之前不推进玻璃/自定义背景；这两项保留在后续需求中，不取消。不开旧的并行工作区，不擅自推送、改 tag 或 Release。

## 逐入口记录格式

在第一阶段台账扩展明细，使用稳定 ID（如 NAV-MAIN-01、COURSE-EDIT-01），每个入口至少记录：

| 字段 | 要回答的问题 |
| --- | --- |
| 入口与任务 | 用户从哪里操作，想完成什么；所属路由/Activity/局部组件及源码位置 |
| 载体及理由 | 原位、展开、单选、面板、确认框、页面、系统界面；为什么适合该任务 |
| 状态与反馈 | 即时生效或草稿确认；保存/失败/重试/取消/重复点击；加载与空态 |
| 导航关系 | 同级/父子/临时覆盖/系统边界；返回到哪里；系统返回、侧滑和层内返回 |
| 动效 | 按压、选中、开关开关两方向、显隐、前进/返回；公共实现引用和参数，任何例外的理由 |
| 连续性 | 初始目标定位、离场内容保留、快速反向、中断、减少动态效果 |
| 配置与证据 | 窗口/语言/主题/字号/键盘/旋转；实测日期、提交、证据位置；未测项 |
| 决策与状态 | 保留/修改/待决定；源码已核对与设备通过分别记录 |

开关只表达独立布尔状态；互斥方案用单选/分段，多项独立选择不能伪装互斥。组件设计遵守 DESIGN_SYSTEM，不为统一而强制所有页面同一种转场。同级切换、父子导航、局部面板、对话框分别表达不同关系。系统拥有的界面单列，不承诺应用完全控制系统动画。

## 性能验收方法

1. 记录构建提交与类型、设备/系统、刷新率、动画设置、字号、温度/电量背景、数据量；使用可分析且尽量接近发布的独立测试包，不覆盖正式包，不暴露签名配置。
2. 分开冷启动/首次进入与预热后的重复切换。先验证录屏能否干扰性能；测量与视觉采样分开。每条高频链同条件至少三组，记录每组结果和异常，不只挑最好的一次。
3. 用 FrameTimeline/Perfetto 等跟踪具体超时帧，将主线程计算、重组/布局、绘制/GPU、系统调度区分。找到代码归因前不宣称某项就是根因；工具无法采集时如实记录限制。
4. 按实际刷新率的帧截止时间判断；同时记录超时帧、P95/P99 和最长停顿。不预设“3% 以下就丝滑”或凭平均 FPS 判合格。以可复现瓶颈消除、同条件无退步和视觉连续为必要条件；若仍有明显卡顿就继续定位。
5. 验收观察：无空白帧/闪顶/离场清空/中途错色/错误滚动；进入返回成对且符合层级，重复与反向操作不跳变；取消手势不误提交；关闭动画仍可正常完成任务。

## 覆盖矩阵与边界

所有入口先验收基准手机操作与返回。公共组件至少覆盖明亮/深色、中英、1.0/1.5 字号；每个受影响页面检查代表性的长文/窄屏，不能只测公共样板。导航需覆盖顶部返回、系统返回、手势完成与取消、快速反复、系统关闭动画。

编辑与选择器覆盖键盘、取消/确认、非首目标、重建；破坏性操作与失败注入使用独立虚构数据。适配覆盖手机、宽屏、短横屏及真实系统分屏/连续跨断点。模拟器尺寸覆盖不等于真平板，StateRestorationTester 不等于旋转或杀进程。每一项缺失设备/条件都记为“待验证”，不写“通过”。

状态统一为：待审 → 已决策 → 已实现/确认保留 → 待验证 → 已通过；实测失败转“需修正”。同一条目可同时具有源码已核对、手机通过、平板待验证等分维状态。没有证据不能提升状态，不把未验证算作失败或通过。

## 问题优先级与防止偏离

- P0：数据丢失/错误写入、崩溃、核心操作不可用，立即处理。
- P1：闪屏、明显卡顿、错误返回/草稿行为、内容或操作被遮挡，优先于装饰。
- P2：组件用途或信息层级不一致、低频体验缺陷，在本工作包修正。
- P3：新材质、新装饰、新功能探索，进入后续队列；不打断当前收口。

新问题先登记：稳定 ID、入口、复现条件、影响、证据、优先级、下一动作。P0/P1 可中断当前批次并写明原因；P2 纳入对应批次；P3 留待基础收口。缺乏证据的性能猜测是调查项，不是已确认缺陷。需要用户决定设计方向时，给出具体对比和建议；日常实现和既有授权内修复自主推进。合并冲突仍按 AGENTS 先讨论。

## 每轮工作与交接

开始：读本文件当前交接、规范相关章节、对应台账；检查 git 状态及真实设备；选择一个主目标和明确退出条件。不得仅依赖聊天记忆，也不得重做已完成工作。

执行：记录复现→决策→最小实现→受影响位置回归。开发中发现新的已授权 P0/P1 持续解决，不因计划里没写就搁置。每批规模以能够完整验证为准，不因一轮结束虚报完成。

结束或上下文交接：更新台账/证据与下方唯一交接块，写明代码提交和验证提交是否一致。对用户报告“完成什么、发现什么、尚未验证什么、下一步是什么”。有代码或资源变更才构建/交付 APK；纯文档不重复构建。阶段进度只统计有固定清单的已决策/已实现/已验证数量，不编造百分比。

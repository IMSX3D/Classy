## 1. 目标与边界

主线始终是：简洁、美观、统一、符合使用直觉，降低认知负担；每处信息、组件和动效都服务于具体任务。

本批五项需求：

1. 降低课程色块的刺眼感，保留课程识别能力与用户偏好的柔和色条。
2. 统一课程块文字位置、字号与信息优先级。
3. 增强关于页品牌卡连续点击反馈与礼花彩蛋。
4. 系统审计代码、纠正注释、清理确认无用的实现，方便新团队接手与吸收上游更新。
5. 明确“学期课表”的用户任务、必要性与首版设计；目前是设计提案，尚未创建页面。

本实施批次允许修改源码、构建与设备验证；不推送、不改tag或Release。后续实施仍在唯一仓库 `仓库克隆目录`；不恢复旧并行工作区。遇到合并冲突先说明方案并与用户商量。

## 3. 新工作项

### READ-01：课程配色

现状与原因：`CourseColorUtil.kt` 的自动配色存在不同明暗/彩度档位；自定义及部分导入颜色可直接用于填充。已有 `softenedIndicator` 主要服务色条，大面积填充未享有同一套柔化规则。只调自动颜色常量可能漏掉实际刺眼的导入颜色。

实施步骤：

1. 清点网格、周列表、今日、冲突课程、桌面组件的颜色来源，区分GROUP/AUTO/CUSTOM、无色开关、灰显及结束状态。
2. 建立浅色/深色样板，包含高饱和自定义色、相近课程色、背景开启/关闭；记录原图作为对照。
3. 提炼“原始课程色→展示底色/识别色条→文字前景色”规则。保留原始存储值与课程色相身份，不重写用户自定义颜色。
4. 以柔和色条为主要方向；填充限制视觉强度，深浅主题分别处理，不靠整卡透明度降低刺眼感。
5. 共用规则推广到实际消费入口；列出保持原样的颜色选择器或兼容路径及理由。

交付：颜色规则、前后样板、调用位置清单、源码与必要的颜色/对比回归。

验收：正文清楚，课程可辨，不因背景改变失去可读性；灰显与正常课程可区别；原始颜色数据不变；重点检查课程名和小字号副信息的最终合成对比度，按普通文字4.5:1作为目标核验。视觉样板需手机/平板、明暗主题对照，算法数值通过不等于审美通过。

### READ-02：课程块文字

现状：`CourseTableView.kt` 中有副信息时课名顶部对齐，无副信息或空间不足时改为居中；基础字号约11sp/9sp后再随课表缩放。不同卡片阅读起点不一致，窄列易省略。

建议方案：课名统一靠上，教室/教师靠下；窄列水平居中；首行与边框保持适量留白。课名约12sp、副信息约10sp仅作为首轮候选，不直接视为最终参数。

实施步骤：

1. 建立1节/多节、长短中英文、缺教室/教师、不同副信息设置、冲突卡及非常规时间样板。
2. 统一顶部基线与底部辅助区，明确最小间距和可用行数预算；不能用固定高度覆盖系统字体放大。
3. 信息优先级为课名→用户选择的主要副信息→次要副信息。缩小空间时先移除次要信息，不无限缩字，也不把课名让位到不可读。
4. 对照桌面网格的密度能力；沿用阅读层级，但不机械复制APP字号。详情始终提供完整内容。

交付：布局尺度与信息降级规则、代表样板、所有相关卡片的消费清单。

验收：课名起点稳定；辅助信息不遮挡课名；1.0/1.5字号、窄/宽/短窗口、长名称可操作；点击完整详情、拖动和冲突切换无回退。保留必要呼吸感，不能只追求塞入更多文字。

### BRAND-03：连续点击与礼花

现状：`ClassyBrandCard.kt` 已有5次连击触发、约850ms的相邻点击间隔判定，主要反馈为卡内星点/连线/扫光；庆祝期间忽略后续触发。该行为存在不易察觉和短暂“点了没反应”的体验风险，并不等于触发逻辑完全失效。

实施步骤：

1. 先验证触摸、键盘、无障碍动作的计数、滚动取消和触发时序，区分“未触发”与“反馈弱”。
2. 建立“有效单击回应→接近阈值的边缘蓄积→触发时释放”的连贯反馈；避免每次同时叠加缩放、震动、闪光。
3. 在卡片两侧设计有限数量的薄荷绿/冰蓝/淡紫礼花，向外喷散并自然消失。独立装饰绘制层避免被卡片圆角裁掉，同时不拦截页面点击或覆盖正文阅读。
4. 首次触发揭示来信入口，后续允许重复庆祝但不自动打开来信。连点不会无限叠加粒子或排队播放。
5. 系统关闭动画时仍直接给出发现反馈与来信入口；离页取消任务，无空闲循环。

交付：交互状态规则、粒子数量/生命周期上限、触发前后与连续操作录屏。

验收：能明显看出成功触发；快速连点、长按、滑动、多指/出界取消不会误触；恢复页面不丢失已发现入口；关闭动画可用；手机/平板按相同目的呈现。对照无礼花基线采样，不能为彩蛋引入持续卡顿。

注释规则：以当前实现为准，解释为什么、边界和兼容要求；删除与常量/算法矛盾的历史叙述；不机械逐行解释语法，不写未经验证的“始终”“完全一致”。复杂公开接口与关键业务规则优先补齐，简单直观代码不堆砌注释。

已发现的审计线索：配色注释与常量/分配规则存在不一致；旧 `SemesterOverviewCard` 无生产调用但仍有测试引用。后者只列为候选，删除前核对全部引用、资源、反射、Manifest、序列化/迁移及外部入口。对应测试若仅维护废弃功能，也需一起评估，不能为了通过测试保留失效设计。

上游吸收：记录上游来源/基线、本地差异、学校适配入口和兼容保留项的用途/验证方法。历史实现优先留Git而非大量注释代码；确需保留的适配层需有当前用途或明确兼容理由。不得以“可能接上游”为由无限保留无主代码。合并冲突先与用户讨论；不自动整仓同步上游。

验收：每个模块有“已审/已修/待处理”状态、源码或文档证据；警告按实际基线分类且不靠全局禁用掩盖；构建和受影响测试通过；数据迁移/学校适配不退步。不以注释行数或删除行数衡量质量，也不承诺一次性清零所有警告。

### SEMESTER-01：学期安排（设计提案）

必要性：周课表回答“这一周怎么上课”，现有课程清单主要展示课程及周次规则；用户还需要直接知道每门课整个学期的具体日期、时间和地点，尤其是单双周、多个时段、不同教室和调休情况。

首版建议：

- 名称「学期安排」，入口在课表“更多”，进入完整页面，不增加主Tab，也不塞入接近全屏的底部面板。
- 默认按课程浏览与搜索，显示主要上课规律和覆盖周次；点击课程显示该学期逐次上课的日期、星期、起止时间、地点。
- 手机使用列表→详情；平板可复用左右双栏。同名不同教师或不属于同一课程身份的安排不可误合并；具体分组规则先核对现有课程模型。
- 初版不加入巨大20周网格、月历、热力图等多套浏览方式。先让“找到课程→看清每次什么时候上”成立，再依据反馈扩展。

设计与实施前置步骤：

1. 盘点现有课程清单能复用的部分，决定是扩展现有任务页还是新增独立入口内容，避免两份重复业务逻辑。
2. 以 `CourseDateResolver`、有效作息与现有调休语义推导日期；核对课程单双周、离散周、非常规时间和课间跨段。不新造一套日期规则。
3. 明确计划课次、灰显/休息标记与已取消之间的差别；没有数据支持时不把灰显课程自动删除或宣称取消。
4. 校验学期边界及跨边界调休、空课表/缺少时间、加载失败、刷新后数据变化与返回位置。
5. 先交付页面结构与虚构数据样板，确定首版范围后再实施；本次仅登记设计，不把方案计为已开发。

未来验收：与周课表/课程详情在同一日期显示一致；每一课次日期、时间、地点可查；无误合并、重复或遗漏；长学期计算不阻塞UI；手机/平板、大字号可阅读；刷新、返回与重建状态有规则。

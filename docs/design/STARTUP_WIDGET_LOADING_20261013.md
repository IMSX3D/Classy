# 冷启动与小组件入口：定点修正

范围：用户提供两段视频，明确重新授权调查冷启动课表和「我的→小组件」。不重启此前搁置的全应用性能项目。

## 结论

- 已修正：数据库未就绪时误显示“没有课表”、先创建第1周网格再跳真实周的中间状态。首次 ready 状态包含课程、有效作息和真实周次；加载期间不创建空态或错误周次的 pager。
- 已修正：小组件管理 VM 用普通 remember 创建、离页不受 ViewModelStore 管理；每次进入重新空列表→实际列表；折叠着的帮助也执行诊断并重复触发列表刷新。改为 Activity 持有并在我的页预读，刷新保留旧列表、合并重叠请求，诊断按展开动作执行。
- **未完成：冷启动总耗时显著缩短、小组件入口首次过渡稳定流畅。** 状态修复不等于 CPU/布局成本消失。本轮不声明两个性能目标都已达标。

## 原因与实验

冷启动原先先发布课表元数据，课程/作息随后 emit，selectedWeek 默认1。Screen 在初始空列表阶段画空态，元数据到达后立即创建 pager；课程与真实周次再到达，造成中途换内容和跳周。热启动保留已完成状态，因此不易复现。

小组件页原先 VM init、AddPanel 显式 refresh、ON_RESUME 均可能查询。完整诊断不该与普通入口绑定。去重和复用已落实，但 Perfetto 表明之后仍有首屏 Compose 重组/测量长帧，不能把所有卡顿归因于 IO。

另尝试短表单 Column 替换 LazyColumn、再移除 Scaffold 子组合。带临时 Debug 测量标记的两次进入，页级测量从约64.53/50.58ms降为18.26/13.85ms；整帧仍约93/67ms，未录屏重复采样也未取得稳定整体收益。**撤回布局实验及临时 Debug 标记**；未修改公共 Scaffold 或原页面外观，避免只移动成本便宣称优化。

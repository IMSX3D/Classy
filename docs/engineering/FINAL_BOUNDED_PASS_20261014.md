## 原因与处理

1. 用户此前实际安装的是 Debug，未启用 R8 优化。首次进入 Compose 页面涉及首次类加载、验证、布局和渲染，热启动已拥有进程及缓存，不能拿热启动推断冷启动没有初始化开销。此次增加 `preview`：继承 Release 优化、沿用 `.debug` 包名与 debug 签名，保留真实测试课表和四个组件绑定。之后体验验收用 Preview，调试/自动化继续用 Debug，独立合成数据性能研究用 Benchmark。
2. 系统启动画面原先在 Room 完整状态之前退出，录屏出现启动底色→加载文字→完整课表。现在等 Compose 提交数据就绪的树后再退出，最多 1500ms，满足就绪即退出，绝非固定等待 1500ms。超时仍允许进入原有稳定加载状态，避免异常数据库把人锁在启动页。这是首帧交接修复，不冒充数据库加速。
3. 原先 `produceState(empty...)` 在课程显示后再补节假日角标和灰显，角标会改变表头高度。改为 IO 读取本地日历快照，与课程状态一起提交；首帧不等网络。新下载的节假日资料、用户修改与重置仍会通知刷新，真实新增资料的变化不能伪装为已预知。缓存改为并发安全容器，避免预加载线程与 UI/组件读写普通 HashMap。
4. 移除 ScheduleViewModel 观察课程时再次全量刷新组件的路径；仓库写入后刷新与 Application 启动恢复保留。减少重复广播、查库及桌面重绘竞争，不把它单独宣称为主要速度收益。

## 实测：同一平板、真实数据、原有四个绑定

vivo PA2553 / Android 16，竖屏 1968×2800、density 400、字体 1.0、动画 1.0、深色；保留实际课表与原有组件。每组冷启动→我的→首次小组件→返回，各三轮；计时不录屏。与前轮无绑定、24条合成课程的 Benchmark 不是同一负载，禁止混算百分比。

| 包 | 小组件链 P95 三轮 | P99 三轮 |
| --- | --- | --- |
| 修改前 Debug | 85 / 69 / 117ms | 150 / 133 / 150ms |
| 修改后 Debug | 125 / 125 / 89ms | 150 / 150 / 150ms |
| 修改后 Preview | 28 / 31 / 29ms | 61 / 57 / 53ms |

同为 Debug 的代码改动没有稳定改善小组件帧耗时；**主要可验证收益来自优化构建及其安装优化状态**，不能把三分之一耗时都记到几行代码上。Preview 的系统 `Displayed` 与 `Fully drawn` 同时为 **179 / 228 / 288ms**；此前 Debug 首个窗口显示不等于内容就绪。这里是 Android 启动计时，非用户手指落下到 OEM 桌面全部动画结束的时间，也不是零初始化成本。

实测安装 dexopt 为 `speed-profile / reason=install`；本轮没有在平板手动强制编译 Preview。OEM 安装器/设备不同，不能承诺每台手机都达到同一数字。最终重打包只补测试版名称资源，未改变执行代码，安装后保留相同签名、数据与组件。

独立录屏逐帧观察：修改前存在中间加载文字；Preview 从启动表面过渡到完整当前周课程，未观察到分批课程出现或中间加载文字。录屏与计时分开，录像 PTS/可变帧率不用于毫秒结论；只按解码帧序列检查画面。自定义照片背景冷解码、未缓存的远端节假日信息和极大课程量不在这份样本里。

# 发布与升级说明维护

## 长期文案规则（所有后续版本适用）

这是用户明确要求的产品规则，后续维护者与开发代理均须遵守，不限于 v0.1.1。

- 应用内更新说明：用 3–6 条简短、通俗的话说明用户能感受到的变化，例如新增什么用途、哪里更方便、修好了什么使用问题。中英文含义一致。
- GitHub Release：开头同样面向普通用户，可补充安装方式、兼容条件和影响使用的已知限制。复杂实现、代码结构、内部任务编号、测试数量和性能分析留在仓库开发文档，用链接供专业读者查看。
- 纯内部重构若没有明确可感知的变化，不硬凑成体验卖点；只描述已经交付且有证据支持的改善，不承诺所有设备“秒开”“绝不卡顿”或未经验证的系统能力。
- 例如：写“从教务更新课程时，会保留你设置的作息时间”，不写“新增来源基线与事务提交校验”；有实测依据时写“首次打开课表时，减少课程陆续出现和画面闪动”，不写“优化异步初始化与首帧渲染”。

发布前逐条人工检查：

- [ ] 普通用户不懂技术术语，也能理解每条说明。
- [ ] 每条体验变化都对应本版已完成的功能或修复，未扩大实测结论。
- [ ] 技术细节已放入仓库文档；用户需要的安装与限制说明仍清楚可见。
- [ ] 应用内说明、Release 摘要与中英文表述一致。

构建检查只能验证版本与语言等结构，不能替代上述文案审阅。

每次发布时：

1. 在 `app/build.gradle.kts` 增加 `versionCode` 并设置 `versionName`。v0.1.0 的应用版本为 `0.1.0`、代码为 `10`，tag 为 `v0.1.0`；后续继续递增内部版本代码，并保持版本名称可递增比较。
2. 更新 `app/src/main/assets/release-notes.json`，填入同一版本号与版本代码。用 3–6 条通俗短句说明用户能感受到的变化，维护简体中文和英语。
3. 执行单元测试、设备测试包编译、Lint 和正式签名构建，并运行教务脚本测试。
4. 创建对应 tag 与 Release，附三种架构 APK、SHA256SUMS 和验证记录。资产名称须保持 `app-<abi>-release.apk`，应用更新检查依赖该命名。

`verifyReleaseNotes` 自动接入 `preBuild`。版本号不一致或缺少任何支持语言的说明都会阻止构建，避免新版本误用旧说明。

升级弹窗由 `WhatsNewDialog` 显示，不依赖网络或检查更新开关。已读版本保存在 `noBackupFilesDir` 的原子文件中；它不会随云备份恢复到另一台设备。升级后只有关闭说明才记录已读，未关闭即退出时，下次打开会继续显示。旧版本没有记录时通过安装时间与更新时间识别升级；全新安装只初始化记录。再次启动与降级不显示，跳过多个版本时显示当前安装版本的说明。
